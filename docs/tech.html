技术方案

为什么只能是
GNOME Shell 扩展

十一条路都试过，每条失败的机制各不相同，但都失败在同一层：窗口。下面是这张死路地图，以及唯一还开着的那扇门。

GNOME Shell 50.1 mutter 18 · Clutter 18 GJS MIT

死路

十一条路，十一个原因

之所以保留这张表：判断「做不到」之前，应该把实现路径列全再逐条否掉——每一条都写清了失败机制和证据。

方案 失败原因 证据
GNOME 自带屏幕键盘只在应用调用 zwp_text_input_v3 时弹；Electron / Chromium 默认不实现。mutter 日志里 text-input 完全为空
--enable-features=TextInputV3flag 名不存在。strings 查不到该字符串

ydotool + uinput注入本身是成功的，但键盘窗口会抢焦点，按键进到了键盘自己身上。注入 OSKOK123 确实出现；点键盘后焦点消失

所有失败都发生在「窗口」这一层。Wayland 的输入隔离不允许普通窗口既接受点击、又不抢焦点；也不允许任何外部进程向别的应用注入按键。只有合成器内部才有这个权限。

原理

两个权限，在同一个进程里

扩展跑在 mutter 进程内部。就这一件事，同时给出了窗口层永远凑不齐的两样东西：注入输入的权限，和「画出来但不参与焦点竞争」的权限。

GNOME Shell 进程同一个进程，没有 IPC
分成两个角色
St 图层Main.layoutManager.addTopChrome
VirtualInputDeviceseat.create_virtual_device
接收点击 / 注入按键事件
应用看到的是一块真实硬件键盘

一个是不抢焦点的 UI，一个是不被拒绝的输入源。

为什么 St 图层不是窗口

addTopChrome 把 actor 放进 shell 自己的 chrome 组——在窗口之上、在 shell 自己的菜单之下。它从不成为 Wayland surface，因此从不参与焦点竞争。点击能到它，因为它 reactive；容器本身 reactive: false，所以空白处的点击照常穿透到下层窗口。

为什么应用分辨不出来

notify_keyval 把按键直接送进 mutter 的输入管线。Xwayland 客户端、原生 Wayland 客户端和 ibus，看到的都是一台普通设备上的普通按键。 

// 特殊键用 X11 keysym
BackSpace 0xff08   Return 0xff0d   Tab  0xff09
Escape    0xff1b   space  0x20
Left 0xff51  Up 0xff52  Right 0xff53  Down 0xff54

GNOME 50 的 typelib 在 /usr/lib/aarch64-linux-gnu/mutter-18/，这一版 Clutter 叫 Clutter-18：Python 的 gi 看不到，只有 GJS 能加载。

中文输入

三条通道，只有一条需要 text-input-v3

这个项目早期一度断言「中文不可能，因为 Electron 不支持 text-input」。这个推理错在路径不全——它只查了一条通道。注入的是真实键盘事件，ibus 照样截获，再走 XIM 把候选词送进应用；Electron 应用跑在 Xwayland 下，所以中文可以输。

通道 谁在用 需要 text-input-v3
zwp_text_input_v3原生 Wayland 的 GTK / Qt 应用需要
XIM（ibus-x11）跑在 Xwayland 下的 X11 客户端 —— QQ、Chrome、Firefox不需要
ibus GTK 模块GTK 应用不需要

怎么切中 / 英

键盘右下角的 中/英 键发 Super+Space，也就是 GNOME 的 switch-input-source。候选词照常：数字键选、空格或 ⏎ 上屏、方向键翻页、⌫ 删拼音、Esc 取消。

粘滞的 ⊞ 会和 Super+Space 打架。 有些 Super 键是粘滞修饰键，点 ⊞ 再点空格同样会触发 Super+Space 而误切输入法。所以 中/英 必须是独立键、直接发完整组合键。

三档尺寸

就地重设样式，绝不重建控件

所有 px 值按 1.00 基准写好，再乘档位缩放。切换时遍历记住的按键表逐个改写 style——因为在一根手指按着的时候重建控件树，抬起事件会落到另一个按钮上。

四个真正要紧的细节

  • 记住每个键：建键时把 {btn, kind, minW, mod} 存起来，重设样式时不用遍历控件树。
  • 一律 Math.round：St/CSS 用小数像素会发虚。
  • 底边不动：记下切换前高度，在 idle_add 里按新高度把 y 回推，于是键盘向上生长、不会跑出屏幕。
  • 别用 get_groups().includes()：GJS 把 gchar** 出参映射成二元组，includes() 永远不匹配，覆盖值会被静默忽略。
# ~/.config/pad-osk/position.kf  —  改完点一下尺寸按钮即可生效
[layout]
size=medium
scale_small=0.72
scale_medium=0.85
scale_large=0.99

允许范围 0.40–2.00。每次保存配置都会把三个 scale_* 原样抄回去，所以调位置不会抹掉手调的数值。

缩放面板占屏宽
0.72927×34955 %
0.851120×42166 %
0.991295×49176 %

按 1696 px 逻辑屏宽实测标定，不是公式外推：Shift / Ctrl 的文字在某些字号下会撑破键位 min-width，让整行变宽、比例漂 1–2 %。

设置面板

不用 PopupMenu，做一层内联面板

1.0 的外观设置没有做成 St.PopupMenu，而是键盘内部的一层内联 sheet：它属于同一个 actor 树，跟着键盘一起缩放、一起透明，也不会去抢输入抓取。

为什么不用 PopupMenu

St.PopupMenu 会自己开一个 grab，点外面任何地方就关；而且它挂在 shell 的菜单层，对一个已经带缩放和偏移的 chrome actor 来说，弹出来的位置是错的。它还会和键盘自己的模态处理打架。

改成键盘容器里的一个 actor 之后：显示/隐藏只是一个标志位，定位和按键用同一套坐标，透明度也自然继承面板那一份。

配色是一张 token 表

每套配色就是五个颜色：底板、键面、修饰键、按下态、强调色。切换时按记住的按键表就地改写 style——和换尺寸同一套路，手指按着的时候不重建控件。position.kf 里的 [custom] 五个值都合法时，颜色行会多出第六个色块。 

# ~/.config/pad-osk/position.kf
[layout]
size=medium
theme=light
opacity=0.60
radius=large
background=/home/user/图片/星空.webp

[custom]
panel=#1b2026
key=#333a42
mod=#3f4750
act=#3a4a4f
on=#7cc4ff

theme 接受 graphite / light / warm / contrast / custom，名字写错回落到深灰；opacity 超出 0.50–1.00 会被夹回边界。

透明度只设一个数

给整个键盘 actor 设 opacity（0–255），mutter 会把父节点的 alpha 乘进每个子节点。于是底板、键面、文字、拖动条和设置面板一起淡，换主题、换尺寸都不用重算一堆半透明叠加。

下限 50 %：再低，浅色壁纸上字就看不清了。读盘和保存时都会夹一次范围。

背景图走系统文件选择器

键盘是 shell 图层，进程里没有可用的 GTK 对话框，所以「选图…」走 XDG desktop portal，退路是 zenity --file-selection，两样都没有就只留 backgrounds/ 的文件列表。铺法是 background-size: cover 等比裁切；图片被删时日志留一行 background missing，自动回退成无背景。

删图要点两下：第一次点 ✕ 只是把它变成「确认删 / 取消」，5 秒不点自动取消——平板上一次误触不该等于删文件。

踩坑

八个最费时间的坑

都已经修好。留在这里，是因为每一条的症状都会把人指向错误的原因。

addTopChrome 传了不认识的参数，控件会「半加入」

GNOME 50 已移除 affectsInputRegion。调用抛出 Unrecognized parameter 时，actor 已经加进了 chrome 层，只是没拿到正确配置。结果是一张覆盖全屏、又不受 GNOME 键盘模块管理的图层。

症状：输入看起来「全死」但画面照常刷新；ui/keyboard.js:1159 maybeHandleEvent 反复抛 Argument descendant may not be null；注销时 shell 卡住不退，超时后被杀。

正确做法：addTopChrome(actor) 不传参数。默认值（不占 strut、不追踪全屏）本来就是我们想要的。

notify_keyval() 不套用 shift level

直接送 ! 的 keysym（0x21）打出来是 1。同一个物理键上的上档字符，必须发基键 keysym + 真实按下 Shift_L。大写字母一直正常，正是因为它走的就是这条路。

同样适用于分号、引号、方括号、逗号、句点、斜杠、反引号、连字符、等号以及整条数字行。

切换修饰键时重建控件，会冒出多余字符

触摸的按下与抬起之间若重建控件，抬起事件可能落到同位置的另一个按钮上，触发多余的 clicked——表现为莫名冒出一个字符。改为就地更新 label.text 与 style。

两个控制入口各管一套状态

系统菜单开关只隐藏面板，应用图标改的是扩展启停，于是「要点两下才生效」。现在两者共用一个状态文件 ~/.config/pad-osk/visible，用 Gio.FileMonitor 监听，写回前先比对当前值，不会形成回环。

这条值得记住：当一个功能有两个控制入口时，它们必须落在同一个状态上，而不是各自实现「看起来差不多」的动作。

折叠按钮不能放在被折叠的容器里

第一版把折叠箭头放进键盘内部那几行，一收起连按钮一起隐藏，就永远展不开了。按钮必须放在始终可见的拖动条上。

GNOME 50 没有任何免重启的代码重载手段

org.gnome.Shell.Eval 被禁用（unsafe-mode 这个键已不存在），ReloadExtension 返回 Method is not implemented，disable + enable 复用缓存的 ES 模块。改一行就要注销一次——这也是为什么三档缩放做成了可调文件。

对一个新建的 KeyFile 调 remove_key()，整次保存就废了

1.0 之前的保存流程是：在新建的 KeyFile 上 remove_key() 清旧值、再写回所有键。在没读过盘的对象上调 remove_key() 会抛异常，save_config 当场中断——位置、尺寸、配色、透明度全都没落盘，日志里只有一行 save config failed，而界面看起来完全正常，所以这个坑很晚才被发现。

教训是：一个会静默失败的设置写入器，比一个会崩的还难查。现在每次保存末尾都做一次读回校验。

选图时，键盘压在自己打开的对话框上

点「选图…」会弹出 XDG portal 的文件选择器，可键盘画在 chrome 图层，永远压在普通窗口之上，结果选择器被键盘挡得只剩一条边。现在选图期间主动隐藏键盘，选择器关闭后恢复——和关机对话框让路用的是同一套监听。

兼容性

需要什么，以及到哪儿为止

一句话：GNOME 50 Wayland，架构不限——安装包标 Architecture: all。

项目要求
设备任何 arm64 平板；实测机型为一加平板 2 Pro（OPD2413 / erhai / SM8750P），其它机型自测。
系统已按上游项目完成 Ubuntu 安装；本仓库只负责触屏输入这一块。
桌面GNOME 50、Wayland 会话。X11 会话、KDE、其它合成器不能用——它依赖 mutter 的 Clutter.VirtualInputDevice 与 Main.layoutManager。
输入法打中文需要 ibus + ibus-libpinyin（已在 Recommends 中声明）。
架构Architecture: all：包内是纯 JS + shell 脚本，没有架构相关文件，arm64 与 amd64 装同一份。

已知限制

  • 只在一加 Pad 2 Pro + GNOME 50 Wayland 上验证过，其它 arm64 平板未测。
  • metadata.json 只声明 shell-version: ["50"]，GNOME 45–49 不会加载；系统大版本升级后可能要改。
  • 三档是绝对像素，按 1696 px 标定；不同逻辑分辨率的平板比例会漂（待办：改为按屏宽比例自适应）。
  • 没有随候选框位置自动避让，键盘停在你放的位置。
  • GDM 登录界面没有屏幕键盘：greeter 是独立用户，看不到用户扩展。
  • 界面跟随系统语言（英文源 + 简体中文翻译）。
  • deb 用 zstd 压缩，需要 dpkg ≥ 1.21.18（Ubuntu 24.04 起自带）。
